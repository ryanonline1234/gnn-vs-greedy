Adjudication · re-run on one machine · code & data

Does the graph neural network beat greedy?

A paper, two formal Comments and two Replies in Nature Machine Intelligence, and nobody moving. So I re-ran it: same host, same graphs, same seeds, both sides implemented from the published papers and code — the Reply’s GraphSAGE variant reconstructed from its text alone — with an answer key.

Corrections: this study has withdrawn two of its own claims — that the Replies’ objection had been “answered on its own terms” (D36, below), and a claimed disagreement with Krutský et al. that compared against their MaxCut rather than their MIS results (D38) — and records its numerical errata in D38. All are in DECISIONS.md.

THE CLAIM

What is actually on trial

“…the graph neural network optimizer performs on par or outperforms existing solvers, with the ability to scale beyond the state of the art to problems with millions of variables.” Schuetz, Brubaker & Katzgraber, Nature Machine Intelligence 4, 367 (2022)
“…a simple greedy algorithm, running in almost linear time, can find solutions for the MIS problem of much better quality than the GNN. The greedy algorithm is faster by a factor of 104…” Angelini & Ricci-Tersenghi, arXiv:2206.13211 (abstract); published as Nature Machine Intelligence 5, 29 (2023), whose own abstract words this differently

The measured object is the validity of a published sentence against an exact objective, not which model is better. That sentence contains two claims, and they are scored separately because they can have different answers.

Claim A · parity with existing solvers

Refuted

A degree-based greedy finds larger independent sets at every degree and every size tested, and at n = 10,000 does it about 204,208× faster on the same machine.

Claim B · scale to millions of variables

Upheld only after repair

Reachable — but not by the released example implementation, which builds a dense n×n matrix (3.6 TiB at n = 106); the paper does not describe its construction at that scale. With a mathematically identical sparse reformulation, a full run still projects to 6.4–8.1 days against greedy's 0.267 s.

Undisclosed · operating range

Fails above d ≈ 7

Past degree seven the network’s raw output is empty in every run (n = 1000, the released implementation’s configuration; a pre-registered re-run at the paper’s smaller embedding finds the same, 0/15 at d = 8, 12, 20, D39). The paper's own experiments sit at degrees three and five.

CONTROL

The measurement nobody in the exchange ran

None of the five documents in the exchange — the original paper, two Comments and two Replies — separates what the network contributes from what the post-processing contributes. Both are needed to produce a reported score, and only one of them is the thing under test.

The separation is available from data already collected: compare the raw thresholded output against the score after repair and maximalization.

Where the network works, the post-processing adds almost nothing — one node in 418 at d = 3. Where the network fails, the post-processing supplies the entire score: at d = 20 the raw output is empty, so the number reported as “PI-GNN” is produced entirely by a first-fit greedy pass over the node order.

This is the sharper form of the comparison, and it forecloses the obvious objection. A reader might suspect the repair-and-maximalize step flatters the network; the decomposition shows it contributes 0.3–2.2% where the network is working, so the measured gap to greedy is the network’s own.

A second control puts an all-ones bitstring — every node selected, carrying no information about the instance — through that same pipeline. It reaches AR 0.8649 at d = 3, n = 10,000 against the trained network’s 0.9138, and at d = 20, n = 10,000 it wins outright (0.15880 against 0.13956). One caveat stated plainly: on an all-ones input every node has the same conflict degree, so the repair pass reduces to iterated maximum-degree deletion — a real heuristic reading the graph. The bitstring carries no information; the pipeline does. That is why the decomposition above, not this control, is the primary evidence.

A trained network scoring below the all-ones null control is not a hyperparameter problem: the next section gives the mechanism, and the one after it tests a pre-registered tuning budget, a post-hoc round, and the GraphSAGE + P = 10 configuration the Reply describes (as implemented here). At d = 20 none of them returns a non-empty raw output (0 of 57 runs).

MECHANISM

Why it fails at high degree: symmetry never breaks

Above degree seven the network's raw output — before any post-processing — is all zeros. My first explanation was wrong, and the way it was wrong is the finding.

I thought the culprit was the diagonal. The published loss is L(p) = pᵀQp with Qᵢᵢ = −1, a pure quadratic form with no linear term, so ∇L(0) = 0 exactly: the empty set is a critical point at every degree. Fixing that should rescue it. It does not. Changing the diagonal to −Σpᵢ removes the critical point, and d = 20 still returns nothing.

The real mechanism is visible when you compare the final training loss against the exact uniform optimum of the modified, linear-diagonal objective (a post-hoc change, not the published loss) — the value a network that learned nothing at all would reach:

Under the modified objective at d = 20, the closed-form mean-field loss is −12.500 and the measurement is −12.499. Measured directly, the output hovers near the uniform value p* = 0.025 with 27–29% scatter and stays more than 6× below the 0.5 threshold. The network is trapped at the mean-field saddle — fluctuations form, but symmetry never breaks.

A caution this page’s first draft got wrong: matching L* does not by itself prove the configuration is uniform. The loss is second-order blind to zero-mean scatter around the stationary point, and two of the three seeds land slightly below L*, which no uniform configuration can do. The trapped-at-the-saddle claim therefore rests on measuring the output vector directly (mean p = 0.0261, standard deviation 27–29% of p*, maximum 0.074 — recorded in results/pstats.jsonl), not on the loss agreement alone.

For the published quadratic diagonal, that uniform solution happens to be p = 0. So “collapses to the empty set” and “stuck at the mean field” are the same event — the formulation simply makes the symmetric solution be nothing, and the fixed 0.5 threshold then reports it as nothing. This also explains why the rescue attempts tried here failed: learning rate, patience and a larger embedding (256) do not cause symmetry breaking. Neither does a smaller one: at the paper’s int(∛n) = 10 the raw output is empty in 15/15 runs at d = 8, 12, 20 (D39).

DEFENCE

Testing the defence the authors actually published

A tuning budget was fixed in writing before any sweep ran — four learning rates × two penalty values × three seeds, at d = 3, 5 and 20 — followed by a separately-labelled post-hoc round with a bigger embedding, longer patience and the repaired objective.

That budget was aimed at the wrong target, and this page previously said otherwise. It was designed against the assumption that the Replies argue the network was under-tuned. Reading the Reply to Angelini (arXiv:2302.03602) shows the defence is two specific changes: “by simply setting P = 10 we find even further consistent improvements. Specifically, for d = 3 at P = 10 GraphSAGE achieves approximation ratios of AR ~ 0.947, on par with the DGA-based results…” — a different architecture and a penalty five times the published one (P = 10 against 2), well above the pre-registered grid, which stopped at P = 3 and never implemented GraphSAGE. The claim that the objection had been “answered on its own terms” is withdrawn.

The defence does not reach the high-degree failure at all: in every one of the 4 configurations — including GraphSAGE with P = 10, as the Reply specifies it — the raw output is empty at d = 20, 12 of 12 runs.

At d = 3, P = 10 moves the GCN slightly in the direction the Reply claims (0.9223 to 0.9289) and still falls short of greedy’s 0.9479 on the same seeds. At d = 5 it makes matters markedly worse (0.8818 to 0.8073, with a non-empty raw output in only 1/3 runs), which the Reply does not mention. These arms were run at d = 3, 5 and 20 only.

One result here is a failure to reproduce, and is reported as nothing more. The Reply states GraphSAGE at P = 10 reaches AR ~ 0.947 for d = 3. This implementation reaches 0.8777 — below its own GCN. The likeliest explanation is that this GraphSAGE is not equivalent to theirs: the Reply gives no architecture detail and no code for it. That is a gap in what can be checked from the published record, not evidence against their number.

The Reply also answers the high-degree benchmark on relevance rather than capability: it calls the d > 16 instances “an interesting academic exercise” but is “not convinced about its practical usefulness”, because real problems are not random regular graphs. That is a different objection from the one measured here. This page concerns random d-regular graphs only, where the ceiling sits at d ≈ 7 (raw output empty in every run from d = 8), below the regime the Reply calls academic; it says nothing about structured real-world graphs.

TIME

The speed gap, actually measured

The published 104 figure was never a controlled measurement. The critique timed its greedy on the authors' own laptop and read the network's times off Figure 5 of the paper it was criticising — different hardware, different conditions. Everything below is one machine, one job at a time, nothing concurrent.

SCALE

Claim B: a million variables

The reference implementation builds a dense torch.zeros(n, n) QUBO matrix. At n = 1,000,000 that is 1.0e+12 float32 entries — 3.6 TiB. The full paper never describes the QUBO construction used at that scale — the word “dense” does not appear in it — so this is a property of the released example implementation, not of a published method description. The sparse reformulation used here is mathematically identical and is what makes any test at this scale possible — a deliberate improvement in the claim’s favour.

The paper sets dim_embedding = int(sqrt(n)) only for n ≥ 105, and int(cbrt(n)) below that; the released notebook, and this study, use int(sqrt(n)) at every n (the embedding column above). From n = 105 up the two agree: dim_embedding = int(sqrt(n)), hidden = dim/2 makes the first layer a dense (n × dim) @ (dim × hidden) matmul, so arithmetic grows as n²/2 regardless of how sparse the graph is. Measured time does not track that cleanly: it grew more slowly than that arithmetic below n = 105, and about 3× faster than it in the last decade, where the 14.9 GiB working set goes memory-bound.

Measured, not projected: after 1,503 s of training at n = 106 — 36 epochs, 0.27% of the schedule this model needs — PI-GNN’s output repairs to 0.37470. The all-ones null control sits at 0.39527, and DGA reached 0.43295 in 0.2671 seconds.

That run was stopped by its wall-clock budget, not by convergence, so it is a lower bound on time-to-parity and nothing more. It does not show the network would never converge. Its raw output fell from 137,531 nodes (epoch 3) to 220 (epoch 36) with the loss still positive, which resembles the high-degree collapse. A traced n = 104 run (one seed) shows the same dip, to 8 nodes at epoch 450, then recovers to 4,097 by epoch 3,000; the n = 106 run stopped far earlier in its schedule than that minimum, so the decay is consistent with the normal early transient (D34). The decay rate depends strongly on n (raw-size ratio 0.95 / 0.56 / 0.0016 over the first 36 epochs at n = 103 / 104 / 106), and that is not explained here.

Projection, and labelled as one. Epochs-to-convergence is stable across three decades (12,361 / 14,812 / 13,321; the n = 105 figure is a single run), so the epoch count transfers. Using the counts measured at the two sizes nearest 106 (13,321 at n = 105, 14,812 at n = 104) and the two measured per-epoch costs at n = 106 (41.75 s from the budgeted run, 47.39 s from the probe), a full run at the released implementation’s configuration would take 6.4–8.1 days, against DGA’s 0.2671 s on the same instance — a factor of roughly 2.1–2.6 million×. The critique claimed 104; this same-host figure is ~208–263× larger, because their 104 compared their own laptop’s greedy against GPU timings read off Figure 5 of the paper they were criticising. Every GNN cost at n = 106 is CPU-only: the faster-device rule (D12) was never executed at this size, an unexecuted protocol step (D33).

The Reply to Angelini reports an updated post-processing (its scaling improves from ~n2.0 to ~n1.0, total run time from ~n1.7 to ~n0.8). The timings on this page are of the original released implementation, followed by this study’s own repair pass (code/repair.c); the updated routine is not tested here. The projection above counts training epochs only.

HONESTY

What would overturn this

Stated plainly, because a verdict that cannot be attacked is not worth much:

  • The port. The original code is DGL 0.5.3 / torch 1.7.1 and will not run on current hardware, so I ported it to plain PyTorch. The repository’s test checks the port’s forward math against the reference’s, re-derived inline — the loss to machine precision against the true asymmetric Q, the convolution to float32 epsilon — and an adversarial audit found it kills the natural mutations of that math except a row-normalisation mutant, because its normalisation check is vacuous on d-regular graphs (D26), and the GraphSAGE layer is untested, because no reference implementation of it exists. The training loop is outside that proof: its fidelity rests on line-by-line replication of the reference’s bookkeeping and on six fresh reruns that matched the recorded results (D26); training is not bit-deterministic, so re-executing a seeded cell can shift its final loss and epoch count slightly (D38). One reporting deviation exists and favours the network: the port keeps the larger of the best and final bitstrings, where the reference keeps best only.
  • The threshold’s location is measured, not derived. The mean-field analysis says where a non-breaking network lands; it does not say why symmetry breaking fails only above d ≈ 6–7 — the uniform point is a strict saddle at every degree.
  • Charity where it counts. Every difference from the reference favours the network: a sparse loss it does not have, and a repair-and-maximalize step it does not perform. The greedy gets none of that. One protocol choice cuts slightly the other way: in the device benchmark at n = 105 the GPU (MPS) was 7% faster than the CPU at d = 3 and 1% slower at d = 5, and every GNN run used the CPU (D14); the check was never repeated at n = 106, an unexecuted protocol step.
  • The mean-field result is a closed form, checked against measurement, not a fit. −12.500 is L* = −n/(2Pd) under the modified objective, derived after that arm had run (D17) and compared with the measured −12.499. Nothing in it is fitted to the data, which makes it the easiest claim here to check.
  • Cells deliberately not run. PI-GNN at d = 5 and d = 20 for n = 105, and at d = 5 for n = 106, were cut on wall-clock grounds after the smaller sizes had already settled those cases — 2.4 hours of machine time for results predictable to three digits, or for a collapse already 10/10 consistent with a closed-form explanation. Their baselines were measured. Saying so beats leaving the gap implicit.
  • Prior art. Much of this is anticipated. The null-control idea is Böther et al., ICLR 2022 (arXiv:2201.10494), for a different method; both failure modes are named by Ichikawa, NeurIPS 2024 (arXiv:2309.16965); the density transition is Krutský et al., ECAI 2025 (arXiv:2507.13703). Their MIS tables put the baseline at zero at d = 10, as here (0/10 non-empty); an earlier version of this repository claimed a disagreement at d = 10 by comparing with their MaxCut result, and that claim is withdrawn (D38). What this study adds on that axis is resolution: its degree grid places the MIS transition at d ≈ 6–7, between their grid points 5 and 10.
  • What I did not test. MaxCut — Boettcher's concurrent critique targets that, and this study is MIS only. Nor does any of this show that graph neural networks cannot do combinatorial optimisation. It shows that this relaxation, with this projection, does not.
METHOD

Reproduce it

559 measurement records on one Apple M1 Pro (10 core, 32 GB). Greedy baselines are C with a bucket queue, so the timing comparison is not distorted by a slow baseline. Instances are uniform random d-regular graphs, verified simple and exactly regular at generation. Seeds control the graph, the network initialisation and the tie-break together.

# Python 3.12
pip install -r requirements.txt
cc -O3 -march=native -o code/greedy code/greedy.c     # drop -march=native if your compiler rejects it
cc -O3 -march=native -o code/repair code/repair.c
python code/test_port.py            # run first — forward-math port-equivalence check; needs nothing else
python code/analyze.py              # summary tables from the committed results
python code/build_report.py && python code/make_site.py      # regenerate report.html and site/
python code/fetch_refs.py           # optional: the papers + the reference implementation into refs/
# To re-measure rather than re-read, write to a NEW file — drivers skip cells already in --out:
python code/runner.py --out results/rerun_phase1.jsonl --d 3 5 20 --n 1000 10000 --seeds 0 1 2 3 4
# collapse_sweep.py, escape_prob.py, escape_d10plus.py and reply_defence.py take no --out: each
# appends to a fixed file in results/ and skips cells already there, so move that file aside first.
# mv -n never overwrites an earlier move-aside; the published files are tracked by git, so
# `git checkout -- results/` restores them.
mkdir -p results.published
mv -n results/collapse.jsonl results/escape.jsonl results.published/
python code/collapse_sweep.py && python code/escape_prob.py && python code/escape_d10plus.py   # escape table: 121 of its 127 runs (the other 6 are phase-1 runs, re-measured by runner.py above)
mv -n results/reply_defence.jsonl results.published/ && python code/reply_defence.py             # the Reply’s defence, GraphSAGE + P=10 (D37)

Code, the raw results/*.jsonl and the decision log are at github.com/ryanonline1234/gnn-vs-greedy; its README carries the same commands.
